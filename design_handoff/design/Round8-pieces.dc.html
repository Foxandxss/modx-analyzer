A hint that disappears after the first capture teaches the app once and then leaves the state undefined for every later session — and this column goes back to dashes every single time the Performance changes (round 6), which is many times an hour. 8e The scope contract, and the caption that lied answers §2d and §2e
The report of TRIGGER ↑0 · 2 CICLOS · 43.8 Hz against a 349.23 Hz carrier is a locking bug for the implementer. The design's job is to write down what the scope guarantees, so that when it cannot deliver it, the panel says so instead of drawing a flat line. Three states, and the caption is the specification.
SCOPE LOCKED 349.23 Hz · 4 CYCLES · 11.5 ms
Four periods of the carrier, with the period boundaries drawn. Four, not two: two periods of bright FM is 5.7 ms and does not visibly repeat, so it cannot show the one thing a scope is for — that the waveform is periodic.
SCOPE NO LOCK · RAW 11.5 ms
It could not lock, so it says so and shows the raw window in amber-dashed — the predicted register, because the time axis is now a claim rather than a measurement. And it names the reason: no held note / pitch unstable / no capture yet.
SCOPE SIGNAL BELOW FLOOR · −101 dB
NOISE FLOOR BAND
The flat line is labelled flat. If peak-to-peak sits under floor + 6 dB, the panel draws the floor band and names it, because a flat trace that looks like a valid trace is the exact failure this project exists to prevent.
THE THREE GUARANTEES, IN WRITING
1 · Which period. The scope locks to the fundamental of the held note — fc from the last capture when there is one, the note's own pitch when there is not. Never a zero-crossing count: bright FM crosses zero many times per period, which is how a 349.23 Hz carrier gets reported as 43.8 Hz, one eighth of it.
2 · How many cycles. Exactly four, always, and the caption states the resulting window in ms so the time axis is never ambiguous.
3 · When it cannot lock. It says NO LOCK, draws the raw window in the predicted register, and names the reason. It never silently draws something that looks locked.
THE WATERFALL CAPTION: COMPUTED, AND SHORTER
The prose half goes. «el ataque brillante apagándose» was a claim about one particular patch — a lovely sentence, hardcoded, and the only thing on screen that lies. There is no version of it that survives live data, because whether the attack is bright is a property of the sound and not of the panel.

What replaces it is the two figures, computed from the actual capture:
WATERFALL · 22 FRAMES · 0 → 712 ms

and the axis labels stay (TIME ↓ · FREQUENCY →). If the app is ever going to say something about the shape — "the index is falling" — it has to be derived from the frames and stamped PREDICTED like every other derived claim. That is a feature, not caption copy, and it is not in this round.

WHY THE TICKET NUMBER IS ON THE CHIP
It is the whole point of the affordance. A panel labelled #5 is visibly on its way out, so nobody designs around it, nobody grows attached to it, and closing the ticket has an obvious UI consequence: the chip disappears and the drawer gets one item shorter. When the last one goes, the handle goes with it and no layout has to be rethought — it was always 52 px on the outside.

Any future instrument docks into the same handle. That is the request answered: one affordance, five ticketed occupants today — bridge, startup, audio, port and sweep, which is what the screenshots actually show — plus the console, which is not ticketed and never leaves. Sized by N, not by the current list.
WHAT IT INHERITS FROM 5c, AND WHAT IT DOES NOT
Inherits: --drawer-grab 52 px, --drawer-lift, the phosphor top edge, opening over the bottom strip, and the rule that nothing inside animates or counts up — nothing in a drawer competes with the signal.

Does not inherit: the ticket, and the alert behaviour. The SysEx console is a designed permanent feature from 5c, not a temporary instrument, so its chip carries no ticket number — which is how you tell the one that stays from the five that go. The SysEx console still calls for attention when there are unconfirmed writes, because an unconfirmed write is a consequence. A bridge log with 0 drops has nothing to say and stays neutral, closed and quiet — a temporary instrument that nags is a temporary instrument nobody closes the ticket on.
